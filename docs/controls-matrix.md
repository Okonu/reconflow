# Controls matrix

Each row gives a risk, its control, how the system enforces the control, and the evidence that an auditor can examine.

| # | Risk | Control | How the system enforces it | Evidence |
|---|---|---|---|---|
| 1 | One person makes and approves their own correction | Segregation of duties (maker-checker) | `AdjustmentPolicy::approve/reject` refuses when `proposed_by` is the current user. The pages, the HTTP routes and the jobs use the same check | Audit events `adjustment.proposed` and `adjustment.approved` with different users. The approve button is disabled and shows the reason |
| 2 | A junior user approves a large correction | Value threshold | An adjustment of more than the threshold ($1,000, a setting with versions) needs `adjustments.approve_high_value` (Finance Manager) | `adjustments.high_value`. Audit event `settings.approvals_changed` shows the history of the threshold |
| 3 | The system posts a correction to the ERP two times | Posting with an idempotency key | Each adjustment has one UUID key. If the ERP gets the same key again, it returns the first journal. A retry uses the same key | Attempts in `erp_postings_out` with the same key. A unique index on `mock_erp_journals.idempotency_key` |
| 4 | An ERP failure loses a correction | A failure state and a retry | A failed posting moves the adjustment and the exception to POSTING_FAILED. An authorised user can retry | `erp_postings_out.succeeded=false`, then `true`. Audit events `adjustment.posting_failed` and `adjustment.posted` |
| 5 | A person changes or deletes the audit trail | Hash chain and append-only storage | Each event keeps a hash of the previous hash and its own data. A database trigger stops updates and deletes, except by the archiver | Audit log → **Verify integrity**. Audit events `audit.verified`. Archive checkpoints |
| 6 | Bad source data causes incorrect matches | Data checks and quarantine | Checks on columns, types, currency, decimal places, dates and duplicates. Rows that fail go into quarantine with a reason. The run does not use them | `quarantined_rows`. The data-quality report on the run and batch pages |
| 7 | A run occurs with missing data | Blocked runs | If a source has no active batch, the run is BLOCKED_DATA (except provisional runs). The system tries again and sends an alert | `recon_runs.status`, `blocked_reason`. The "run blocked" notification |
| 8 | Nobody can reproduce a result later | Runs with versions and batches that do not change | A run keeps a copy of the rule settings and the batch versions. A new run makes a new version. It never writes over an old run | `recon_runs.rule_config`, `batches`, `superseded_by_id` |
| 9 | A user gets access to a function without authority | Access control by permission | A policy checks the permission for each action. Roles are data. An architecture test stops checks on role names | The Roles page. The permission contract test. Audit events `role.*` |
| 10 | Too many users see personal data | Masking by default and audited unmasking | Phone numbers are masked on pages and in exports. To unmask, a user needs `pii.unmask` and must give a purpose. An unmasked export needs `results.export_unmasked` and a reason | Audit events `pii.unmasked` and `report.exported` (masked=false, reason) |
| 11 | Signed-off figures change | Date lock | After sign-off, a date cannot have a new run or a confirmed upload. To reopen a date, a user needs `runs.reopen` and must give a reason | `run_signoffs`. Audit events `run.signed_off` and `run.reopened`. A 409 conflict for locked actions |
| 12 | A manager signs off a date with open material issues | Sign-off blockers | Open High or Critical exceptions, unconfirmed fuzzy matches, and provisional or stale runs stop sign-off. Carried exceptions need a comment | Blockers on the Sign-off page. `run_signoffs.carried_exception_ids` and the comment |
| 13 | Users accept fuzzy matches without a check | Human confirmation | A person must confirm or reject each MATCHED_FUZZY item. A rejection makes two exceptions. The system remembers it at each new run | `recon_match_reviews`. Audit events `match.fuzzy_*` |
| 14 | Exceptions get old and nobody sees them | Severity, due dates and owners | The value at risk sets the severity and the due date. The system assigns an owner. Filters, dashboard figures and alerts show overdue items | `exceptions.due_at`, `owner_id`. Notifications. The dashboard |
| 15 | A user acts on AI output without a check | A person decides | The AI writes only to `ai_suggestions`. AI output changes no state. The system records each accept or override. An override needs a reason | `ai_suggestions.status`, `decision_reason`. Audit events `ai.*`. The oversight page |
| 16 | Personal data goes to the AI provider | Redaction | The `Redactor` replaces phone numbers and agent IDs with salted tokens and removes personal data from the payload. The stored input and its hash show exactly what the system sent | `ai_suggestions.input`, `input_hash`. The data protection document |
| 17 | The AI does not operate correctly in production | Kill switch and monitoring | An audited switch turns the AI off for all users. The system then uses the rules only. The system monitors acceptance, overrides, failures and confidence. An evaluation set tests each prompt change | The oversight page. Audit event `ai.kill_switch_toggled`. `ai_eval_runs` |
| 18 | A person changes a setting and leaves no record | Settings with versions and audit | Each save makes a new version with the author and a reason | `recon_rule_configs`, `setting_versions`. Audit events `config.created` and `settings.*` |
| 19 | The system keeps personal data too long | Retention | A daily job anonymises transactions after 7 years. The system deletes AI logs after 12 months and archives the audit trail after 7 years. An erasure request anonymises the data immediately | Audit events `retention.*`, `privacy.subject_erased` and `ai.logs_pruned` |
| 20 | An export contains a formula attack | Safe exports | The system escapes cells that start with `=`, `+`, `-` or `@` in CSV and XLSX files | `SpreadsheetSafe`. The export files |
| 21 | An attacker tries many passwords | Login limits and strong hashes | Login attempts are limited. Passwords use Argon2id and a password policy. Accounts can be deactivated. Session cookies are secure | Audit events `auth.*` |
| 22 | Web attacks (XSS, clickjacking, CSRF) | Security headers | CSP with nonces, `X-Frame-Options: DENY`, HSTS with TLS, CSRF protection and same-site cookies | The response headers. The `SecurityHeaders` middleware |
