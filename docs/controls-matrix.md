# Controls matrix

Each row: the risk, the control, how the system enforces it, and the evidence an auditor can inspect.

| # | Risk | Control | How it is enforced | Evidence |
|---|---|---|---|---|
| 1 | One person creates and approves their own correction | Segregation of duties (maker-checker) | `AdjustmentPolicy::approve/reject` denies when `proposed_by` = current user; the check runs for UI, HTTP and jobs alike | Audit `adjustment.proposed` and `adjustment.approved` with different actors; disabled approve button with the SoD reason |
| 2 | Large corrections approved by junior staff | Value threshold | Adjustments above the threshold ($1,000, versioned setting) need `adjustments.approve_high_value` (Finance Manager) | `adjustments.high_value`; audit `settings.approvals_changed` for threshold history |
| 3 | A correction is posted twice to the ERP | Idempotent posting | One UUID idempotency key per adjustment; the ERP replays the original journal for a repeated key; retries reuse the key | `erp_postings_out` attempts with the same key; unique index on `mock_erp_journals.idempotency_key` |
| 4 | ERP outage loses a correction | Explicit failure state and retry | Failed posts move the adjustment and exception to POSTING_FAILED; an authorised user retries | `erp_postings_out.succeeded=false` then `true`; audit `adjustment.posting_failed`, `adjustment.posted` |
| 5 | Audit trail altered or deleted | Hash chain and append-only storage | Each event hashes the previous hash plus its canonical payload; a DB trigger blocks UPDATE and DELETE except the checkpointed archiver | Audit log → **Verify integrity**; `audit.verified` events; archive checkpoints |
| 6 | Bad source data produces wrong matches | DQ validation and quarantine | Schema, type, currency, decimal-place, date-window and duplicate checks; failing rows are quarantined with reasons and excluded | `quarantined_rows`; DQ report on run detail and batch pages |
| 7 | Reconciling with missing data | Blocked runs | A run without an active batch for every source is BLOCKED_DATA (except provisional runs), retried and alerted | `recon_runs.status`, `blocked_reason`; run-blocked notification |
| 8 | Results can't be reproduced later | Versioned runs and immutable batches | Runs store the rule snapshot and exact batch versions; re-runs create new versions and never overwrite | `recon_runs.rule_config`, `batches`, `superseded_by_id` |
| 9 | Unauthorised access to functions | Permission-based RBAC | Every action goes through a policy that checks permission codes; roles are data; an architecture test forbids role-name checks | Roles page; permission contract test; audit `role.*` events |
| 10 | Excessive access to personal data | Masking by default, audited unmask | Phones are masked in UI and exports; unmask needs `pii.unmask` plus a stated purpose; unmasked export needs `results.export_unmasked` plus a reason | Audit `pii.unmasked`, `report.exported` (masked=false, reason) |
| 11 | Signed-off figures change afterwards | Date lock | Sign-off locks re-runs and upload confirmation for the date; reopening needs `runs.reopen` and a reason | `run_signoffs`; audit `run.signed_off`, `run.reopened`; 409 conflict on locked actions |
| 12 | Sign-off with unresolved material issues | Sign-off blockers | High/Critical open exceptions, unreviewed fuzzy matches and provisional or stale runs block sign-off; carried exceptions need an acknowledgement comment | Sign-off page blockers; `run_signoffs.carried_exception_ids`, comment |
| 13 | Fuzzy matches accepted blindly | Human confirmation | MATCHED_FUZZY items must be confirmed or rejected; a rejection splits them into exceptions and is remembered on re-runs | `recon_match_reviews`; audit `match.fuzzy_*` |
| 14 | Exceptions age unnoticed | Severity, SLA and ownership | Severity from value at risk, SLA due dates, auto-assignment, overdue filters and dashboard tiles, critical alerts | `exceptions.due_at`, `owner_id`; notifications; dashboard |
| 15 | AI output acted on without review | Human in the loop | AI writes only `ai_suggestions`; no state change follows from AI output; accept or override (reason required) is recorded | `ai_suggestions.status`, `decision_reason`; audit `ai.*`; oversight page |
| 16 | Personal data sent to the AI provider | Redaction | `Redactor` replaces phones and agents with salted tokens and scrubs the payload; the stored input and its hash show exactly what was sent | `ai_suggestions.input`, `input_hash`; data-protection doc |
| 17 | AI misbehaves in production | Kill switch and monitoring | A global off switch (audited) falls back to rules-only; acceptance, override, failure and confidence are tracked; an eval set gates prompt changes | Oversight page; `ai.kill_switch_toggled`; `ai_eval_runs` |
| 18 | Settings changed without trace | Versioned, audited settings | Every save creates a new version with author and reason | `recon_rule_configs`, `setting_versions`; audit `config.created`, `settings.*` |
| 19 | Personal data kept too long | Retention | Transactions are anonymised after 7 years (daily job), AI logs deleted after 12 months, audit archived after 7 years; erasure requests anonymise on demand | Audit `retention.*`, `privacy.subject_erased`, `ai.logs_pruned` |
| 20 | Formula injection through exports | Safe exports | Cells starting with `= + - @` are escaped in CSV and XLSX | `SpreadsheetSafe`; export files |
| 21 | Credential stuffing / brute force | Login throttling and strong hashing | Throttled login, Argon2id, password policy, deactivation, secure session cookies | Audit `auth.*` events |
| 22 | Web attacks (XSS, clickjacking, CSRF) | Security headers | CSP with nonces, `X-Frame-Options: DENY`, HSTS behind TLS, CSRF protection, same-site cookies | Response headers; `SecurityHeaders` middleware |
